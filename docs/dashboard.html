Dashboard Usage Guide

The NetScan dashboard is a fully server-rendered, HTMX-powered interface for managing subnets, inspecting IP states, triggering scans, and monitoring background jobs. There is no JavaScript build step — the UI is served directly by FastAPI and updated via HTMX partial swaps.

Access URLs

Once the dev server is running, the following endpoints are available:

URL Description
localhost:8000 Dashboard home — redirect to login or subnet list
localhost:8000/docs Interactive OpenAPI / Swagger documentation
localhost:8000/redoc ReDoc API reference
localhost:8000/health System health endpoint (returns JSON status)
Note: The dashboard is protected behind session-based authentication. You must log in before accessing any dashboard page. The /health endpoint is exempt from rate limiting but does not require authentication.

Authentication

The dashboard uses session-based authentication via the DASHBOARD_PASSWORD environment variable. This is separate from the API key authentication used by the REST endpoints.

Login Flow

  1. Navigate to localhost:8000 and you will be redirected to /login.
  2. Enter the DASHBOARD_PASSWORD and a valid, active API key.
  3. On success, the server stores the API key in a signed session cookie and redirects to the dashboard home.
  4. All subsequent HTMX requests automatically inject the X-API-Key header via a global htmx:configRequest event listener.

Session Cookies vs API Keys

Mechanism Used By Scope
Session cookie Browser dashboard Stores the API key server-side; CSRF-protected form submissions for login
API key header REST API + HTMX calls X-API-Key header sent with every request; role-based (admin, operator, read_only)
Security: The login form uses CSRF tokens generated from the session ID and secret key. Tokens expire after 30 minutes. The session cookie is signed and cannot be tampered with.

Subnet Overview

The main dashboard view (/) displays all configured subnets as cards with live statistics and a color-coded status summary.

Summary Metrics

At the top of the page, four metric cards show aggregate counts across all subnets:

  • Tracked Subnets — total number of configured CIDR blocks
  • Active Detected — IPs that responded to probes and are confirmed alive
  • Uncertain / Quarantine — IPs that went silent and are in quarantine before release
  • Available Candidates — IPs not yet assigned, reserved, or detected — safe to allocate

Subnet Cards

Each subnet card shows:

  • CIDR block and pool label (name)
  • Scan interval and quarantine configuration
  • Netmask and usable host count
  • Color-coded status breakdown (active / uncertain / reserved / available)
  • A proportional progress bar showing state distribution
  • Action buttons: IP Matrix (opens the CIDR grid) and Scan Now (triggers an immediate scan)

CIDR Matrix Grid

Clicking IP Matrix on a subnet card opens a dense tile grid showing every IP address in the CIDR range. Each tile is color-coded by state:

Color State Meaning
■ ACTIVE_DETECTED Host responded to the latest probe — confirmed alive
■ UNCERTAIN_FIREWALLED Host went silent; in quarantine period before release
■ ASSIGNED_RESERVED Manually reserved by an operator — will not be auto-released
■ AVAILABLE_CANDIDATE Not tracked or confirmed free — safe to allocate

Each tile displays the last octet of the IP address. Hover for the full address. Click any tile to open the inspector drawer.

Design note: The matrix grid uses responsive Tailwind columns (8 on mobile up to 32 on wide screens) with a 1.5-unit gap. Tiles scale on hover with a subtle transform effect.

IP Inspector

Clicking any IP tile in the matrix grid opens a slide-over drawer from the right side of the screen. The drawer is loaded via HTMX partial swap (hx-get on the IP endpoint).

Details Shown

The inspector displays the full IP record with these fields:

Field Description
ip Full IPv4 address
status Current state badge (color-coded)
hostname Reverse DNS hostname (if resolved)
mac_address MAC address (available only via L2 ARP probes)
mac_vendor Hardware vendor from MAC OUI lookup
discovery_method Probe type used: ARP, ICMP, or TCP SYN
consecutive_misses Number of scans in a row without a response
last_seen_at Timestamp of last confirmed response
last_scanned_at Timestamp of last probe attempt

Open Ports

If the scanner detected open TCP ports, they are listed below the properties with port number, protocol, service name, and product (if identified by nmap).

Reservation Toggle

A form at the bottom of the drawer allows you to:

  • Lock as Reserved — toggle the IP to ASSIGNED_RESERVED state (prevents auto-release)
  • Custom Hostname — set a custom alias for the IP

Changes are submitted via PATCH /api/v1/ips/{ip} with the session API key.

Audit Timeline

If history records exist for the IP, a scrollable timeline shows every state transition: the event type, old status, new status, and timestamp. This provides a full audit trail for compliance and debugging.

Creating Subnets

Click Add Subnet CIDR on the dashboard home to open the creation modal.

Form Fields

Field Required Default Description
cidr Yes — IPv4 CIDR block (e.g. 192.168.1.0/24)
name Yes — Pool label (e.g. "Server Farm", "DMZ")
scan_interval_minutes No 60 How often to auto-scan (0 = manual only)
quarantine_hours No 48 Hours before an uncertain IP can be released
description No — Free-text notes about this subnet
miss_threshold No 3 Consecutive misses before marking uncertain

CIDR Validation

The server validates that the CIDR is a valid IPv4 block. The dashboard expands the CIDR to calculate usable host count and displays it on the subnet card after creation.

What Happens After Creation

  1. The subnet record is persisted to the database.
  2. If scan_interval_minutes > 0, the APScheduler background service automatically registers a recurring scan job.
  3. The dashboard refreshes to show the new subnet card with initial stats (all IPs start as AVAILABLE_CANDIDATE).

Running Scans

Scans can be triggered manually or run on a schedule. The scan job monitor page (/scans) shows execution history and real-time status.

Manual Scan Trigger

Two ways to trigger a scan:

  • From the subnet card — click the Scan Now button. The button shows a spinner during execution and the page reloads after ~3 seconds.
  • From the matrix view — click Trigger Scan in the header area of the CIDR grid page.

Both call POST /api/v1/subnets/{id}/scan via HTMX and update the UI without a full page reload.

Scan Job Monitor

Navigate to Scan Jobs in the top nav to see a table of all recent scan jobs. Each row shows:

Column Description
Job ID Truncated UUID of the scan job
Subnet CIDR block that was scanned
Status QUEUED, RUNNING, COMPLETED, or FAILED
Trigger What initiated the scan (manual, scheduled, etc.)
Results Active / Uncertain / Available counts at completion
Started / Completed Timestamps for the job lifecycle

Real-Time Updates

Running scans display a pulsing RUNNING badge. The table shows up to the last 100 scan jobs. For programmatic access, use GET /api/v1/scans with the API key.

Concurrency: The scanner uses an asyncio semaphore to limit concurrent nmap processes. Multiple scan jobs may be queued, but only a configured number execute in parallel.

IP Management

The dashboard provides visual tools for managing IP reservations and understanding state transitions.

Reserving IPs

  1. Open the matrix grid for the target subnet.
  2. Click the IP tile you want to reserve.
  3. In the inspector drawer, toggle Lock as Assigned / Reserved.
  4. Optionally set a custom hostname or alias.
  5. Click Save Changes.

The IP transitions to ASSIGNED_RESERVED and will not be auto-released by the quarantine system. It also will not appear as an available candidate for provisioning.

Releasing Reserved IPs

To release a reserved IP, follow the same steps above but uncheck the Lock as Assigned / Reserved toggle. The IP returns to AVAILABLE_CANDIDATE and will be considered for allocation again.

Viewing IP History

The Audit Log & State Transitions section in the inspector drawer shows a scrollable timeline of every state change for the IP. Each entry includes:

  • Event type — what triggered the change (scan result, manual reservation, etc.)
  • Old status → New status — the state transition
  • Timestamp — when the transition occurred

Understanding State Transitions

The following diagram shows the normal lifecycle of an IP address in NetScan:

AVAILABLE_CANDIDATE → ACTIVE_DETECTED → UNCERTAIN_FIREWALLED → AVAILABLE_CANDIDATE

An IP can also be manually set to ASSIGNED_RESERVED from any active or uncertain state. Reserved IPs skip the quarantine logic entirely.

Settings

The Settings page (/settings) provides management for API keys and outbound webhook integrations.

API Key Management

View all existing API keys with their name, prefix, role, and last-used timestamp. From this page you can:

  • Generate Key — create a new key with a label and role (admin, operator, read_only)
  • Revoke Key — permanently deactivate a key (via DELETE /api/v1/auth/keys/{id})

Generated keys are shown once at creation time. The dashboard stores only the prefix and hash.

Webhook Configuration

Register outbound webhooks to receive HMAC-SHA256 signed JSON payloads when IP state changes occur. For each webhook you can:

  • Register Webhook — provide a name and endpoint URL; a signing secret is generated automatically
  • Test Payload — send a test event to verify connectivity
  • Delete — remove a webhook endpoint

The signing secret is displayed only once at creation. Webhook payloads include the full IP object and are signed with HMAC-SHA256 for verification at the receiver.

System Health

Access GET /health for a JSON response indicating system status. This endpoint is exempt from rate limiting and is useful for uptime monitoring and load balancer health checks.

Keyboard Shortcuts

The dashboard relies on browser-native navigation and HTMX partial updates. While there are no custom keyboard shortcuts, these patterns improve efficiency:

Action Method
Navigate between nav links Tab / Shift+Tab to focus, Enter to activate
Focus the IP matrix grid Click any tile; arrow keys move focus in most browsers
Close the inspector drawer Click the X button, or press Esc if focused
Close a modal Click the backdrop, click Cancel, or press Esc
Trigger a scan via keyboard Tab to the Scan Now button, press Enter
Refresh the scan job list Browser refresh — the page is server-rendered, no client state to lose

Tips

Best practices for using the NetScan dashboard effectively:

✓ Start with a small CIDR (/28 or /27) to verify probe detection works on your network before scanning large ranges.
✓ Set scan_interval_minutes to 0 for subnets you only want to scan manually — avoids unnecessary nmap runs on sensitive networks.
✓ Reserve IPs immediately after provisioning them in your infrastructure to prevent the dashboard from marking them as available.
✓ Monitor the Uncertain / Quarantine count on subnet cards. A growing number may indicate a network issue or firewall change.
✓ Use the IP history timeline to trace when a host went down — this helps correlate with infrastructure changes or outages.
✓ Generate separate API keys for different integrations (CI/CD, Terraform, monitoring) so you can revoke them independently.
✓ Register a webhook pointing to your SIEM or alerting system to get real-time notifications on state transitions.
✓ Check /health from your monitoring platform to track uptime. It is exempt from rate limiting.
✓ Use the Available IP Finder page (/provision) to quickly find free IPs across all subnets without manually inspecting each matrix.
✓ Keep the DASHBOARD_PASSWORD strong and unique. The session is signed with SECRET_KEY — both must be set in production.
Warning: Never share the dashboard session cookie or expose the dashboard on a public network without TLS. The session transmits the API key in a signed cookie, and all HTMX requests inject it into headers automatically.
